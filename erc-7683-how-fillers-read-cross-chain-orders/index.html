ERC-7683: How fillers read cross-chain orders

What is the ERC-7683 cross-chain intents standard? It gives intent protocols a shared order format and solver interface, while leaving settlement proof to each protocol.

Crypto Bulletin Newsroom Nov 28, 2026 · 07:22 UTC 2 min read

For DeFi users and builders comparing intent flows, ERC-7683 is a proposed standard for describing orders to fillers, so they can evaluate orders across protocols through shared interfaces.

The design has evolved. The earlier cross-chain order version defined `GaslessCrossChainOrder` and `OnchainCrossChainOrder`, which an origin settler could open through `open` or `openFor`; a destination settler exposed `fill`. The current ERC text describes these as parts of an earlier draft. Its present design uses protocol-specific order payloads and a resolver that translates them into a common solver-facing representation. The ERC-7683 specification explains the current resolver model and notes what the earlier interfaces covered.

In the earlier order format, `orderDataType` identifies the protocol-specific data type, while `orderData` carries the terms in that type. This shared envelope lets fillers recognize common order fields without treating every protocol’s payload as identical. In the current design, a resolver interprets the payload and returns common instructions for solvers to assess.

Consider an Across intent route quoted on Jumper bridge: the user opens an order on the origin chain, a filler delivers the requested asset on the destination, and protocol settlement repays the filler. Jumper bridge aggregates routes through supported bridges and swaps; it can help surface a route, while ERC-7683 concerns how an intent protocol describes orders for fillers. For details on route selection and transfers, see Jumper bridge routes; Jumper bridge is the routing layer in this example, not the standard.

Across’s documentation describes this front-fill-then-settle pattern: relayers use their own capital to fill on the destination chain and await reimbursement through settlement. The exact proof and repayment path depend on the protocol. ERC-7683 standardizes the order description and solver-facing interface; it does not prescribe one settlement contract, oracle, or messaging system.

That boundary matters when assessing trust. A common format can let more fillers evaluate orders from more compliant protocols, pooling solver participation instead of requiring a separate integration for every payload. But interoperability does not make settlement trustless by itself: fillers still rely on the specific resolver and settlement contracts, plus the protocol’s method for proving a fill and repaying them.

So when reading an ERC-7683 order, inspect its protocol-specific terms and identify which resolver or settler interprets them. Then check how that protocol verifies destination execution and makes filler repayment final. The shared interface helps you compare orders; the protocol’s settlement design tells you where trust sits.
